驱动：`behavior_r1pro`

BEHAVIOR 官方评测器负责仿真时间、重置、终止条件、评分和视频。
驱动通过评测器的 WebSocket 连接，按次授予有限的动作执行步数。
Agent 推理期间，仿真时间暂停。

## 坐标系与状态约定

以下动作使用的所有实测位置都必须位于 `robot_base` 坐标系，即
`artifacts/observations/observation.json` 中指定的坐标系。在该坐标系中，
+X 指向前方，+Y 指向左方，+Z 指向上方。绝不能直接把图像像素坐标当作公制动作坐标。

观测清单包含三个已标定的 RGB-D 视角（`head`、`left_wrist` 和
`right_wrist`）、官方全分辨率图像的精确相机内参、以米为单位的
`depth_linear` 深度数组、相对于机器人底盘的相机坐标变换，以及结构化的
R1Pro 本体感知状态。`ROBOT_STATE.md` 中的 `robots.behavior_r1pro`
包含实时的评测器和网关状态。每次物理动作后，都要重新读取这两个文件。

## 目标身份识别

目标存在歧义时，应结合：

`物体类别 + 外观特征 + 原始任务关系`

综合使用形状、颜色和可见细节；光照可能改变单一颜色线索。根据原始任务关系
绑定目标，并在运动后持续追踪同一实例。追踪连续性丢失时，应重新确认身份，
而不是换成另一个同类物体。

### 物体外观提示

- **收音机：** 当前收音机实验中观察到的资产具有红色机身、浅色边框和深色
  圆形扬声器区域。应结合任务中的桌子及房间关系识别，不能仅凭一块红色区域
  确认目标。不同实例的资产和朝向可能不同，应确认当前外观，而不是要求所有
  收音机都具有这一配色。

### 可观察状态提示

- **OmniGibson 开关标记：** 能够辨认且看得到物体真正的开关状态标记时，
  **红色表示关闭，绿色表示开启**。这是仿真器的标记约定，不是所有电器
  LED 指示灯的通用规则。
- 区分状态标记与收音机的红色外壳、扬声器细节、反光及其它彩色像素。
  明亮的红点不能证明收音机已开机；任意绿色区域也不等于开启状态标记。
- 标记被裁切、遮挡、过小或无法可靠辨认时，将开关状态报告为不确定。
  缺少视觉证据不能证明物体处于关闭状态。视觉状态证据不能替代下文定义的
  官方成功信号。

### 向子 Agent 传递身份与状态信息

`object_location` 和 `task_verification` 子 Agent 不会自动继承本 profile。
每次委托请求都应自包含：提供目标的相关外观、原始任务关系及排除条件。
请求验证开关状态时，明确传递“标记红色为关、绿色为开”的约定，并要求在
无法辨认标记时报告不确定。请求针对目标物体提供证据，而不是笼统声称
“某个灯亮了”。

如果 `PLAN.md` 中的视觉 `done_criterion` 依赖这一标记，也应在其中写明相关
标记约定；后台视觉监控器接收该判据，而不是本 profile。这些提示用于感知和
验证请求，不改变冠军策略必须原样使用 `effective_prompt` 的约定。

## 默认任务流程

遵循原生 EMERGE 中“实测几何引导粗运动、视觉引导精细交互”的分工。
底盘站位与末端位置是两件事：头部画面中目标看起来很近，不代表手已经处于
合适的预操作姿态。在 `PLAN.md` 中记录任务级里程碑；导航和机械臂动作的细节
在执行时根据当前证据选择。

目标需要粗接近时，默认的技能交接关系是：

`判断底盘站位 → 必要时导航 → 定位目标 → 必要时 attach/IK 预接近 → 确认实测姿态 → VLA 精细交互`

1. **建立合适的底盘站位。** 根据当前观测判断目标可见性、操作侧和可见障碍；
   需要时使用 `task_verification`。需要底盘移动或调整位置时调用 `lightnav`
   技能；底盘站位已合适时跳过。导航停止或视觉上判断“已经靠近”，不能证明
   手臂可达、身体有足够通行间隙或末端已准备就绪。
2. **测量当前运动目标。** 目标可见且需要机械臂粗接近时，委派
   `object_location`；仅阅读其技能说明不等于执行定位。请求中应包含目标身份、
   任务关系以及相关支撑面和障碍几何，并要求以 `robot_base` 返回结果。
   只使用成功、无歧义且 `found: true` 的实测几何结果。定位需要配置的 SAM3
   服务；服务失败或 `found: false` 都不能作为动作目标。底盘运动后，不能未经
   新观测重新确认就复用旧的底盘相对坐标；目标发生移动后应重新定位。
3. **将末端带到预操作区域。** 定位成功后，需要沿可见空旷路径粗接近时，使用
   现有 `attach` 技能及基于 IK 的 `move_to_pose`，指定 `coarse: true`。
   根据当前实测几何和任务需求选择手臂；左右手均无默认优先级。
   所选接近方式应为后续交互保留可用空间。
   当几何可靠、路径明确且手尚未处于合适位置时，这是默认的下一项控制动作。
   根据实测几何选择物体占据体积外的预接触点；不要以物体中心为目标，不要猜测
   控件位置，也不要用规则动作推物体。将当前手腕朝向作为偏好，而不是精确抓姿。
   接受有帮助的部分接近，不要仅为缩小剩余距离反复调用 IK。检查实际状态后，
   将精细对准与接触交给 VLA。仅在有独立依据的短距离直线运动中使用
   `move_linear`，不要用它再次近似尝试同一目标点。
   遵守下文 R1Pro 参数约定，不要直接复制其它机器人的动作参数。
   关节限位和 IK 收敛都不等于碰撞检查。
4. **确认实测手部姿态。** 重新读取同步的 `ROBOT_STATE.md`，比较实测末端
   姿态与预接近目标。接触、遮挡或通行间隙不明确时，使用当前相机证据确认。
   IK 求解成功或指令执行结束都不证明物理到位。判断操作里程碑是否达成时，
   必须分别考虑底盘站位是否合适、手部是否已准备就绪。
5. **将精细交互交给 VLA。** 把最后的手部视觉对准、抓取、放置和机构操作
   交由冠军策略处理。局部目标写在 `PLAN.md` 和
   动作推理中；每次 VLA 调用仍须原样使用
   运行时 `effective_prompt`，不能改写成局部阶段指令。策略保留全身控制权，
   接管后仍可能调整位置；不引入锁底盘机制。
6. **重新判断进展并恢复。** 动作后检查实际状态及相关可见变化，而不仅是执行
   是否正常。`step_completed`、`state_synced` 和评测器仍在运行，都不是任务
   取得进展的证据。遵循规划技能的重试与恢复规则；单纯增加 VLA 预算不算恢复。

如果当前证据已表明手处于合适的预操作区域，可以跳过多余的 IK。若无法建立可靠
几何或明确的粗运动路径，或者选择接近方式本身需要精细视觉对准，应改善观测，
或有依据地让 VLA 处理该接近过程。固定关节机构的接触仍由视觉引导；不要用
`attach` 拉动或操作机构。在计划或动作推理中说明跳过默认交接的证据或理由；
VLA 能控制全身，本身不是跳过可行的实测几何粗接近的理由。不要为强行执行
该流程而编造坐标，也不要仅增加步数重复同一个失败的 IK 目标。

## 技能职责

- `lightnav`：通过 `navigate_vln` 执行底盘移动和站位调整。
- `object_location`：测量目标及影响运动间隙的相关几何，不执行运动。
- `attach`：通过受支持的 IK 运动原语执行实测几何引导的机械臂预接近及空旷
  路径搬运，并在精细接触前停止。
- `task_verification`：判断可见场景状态和任务关系，不提供公制坐标、可达性
  保证或官方成功信号。
- `vla`：通过冠军策略完成最终对准及接触密集的交互操作。

## 支持的动作

以下示例仅演示参数格式，不代表默认手别。

### `vla_execute`

调用冠军 PI_BEHAVIOR 策略；该策略可以控制全身运动和依赖视觉精度的接触操作。
网关原样转发全部 23 维动作，包括底盘 x/y 平移速度和偏航角速度。
没有 navigation/manipulation 控制模式切换。VLA 能自行接近目标和调整位置，
但适合采用实测几何粗接近时，应遵循上述默认流程。先使用 LightNav 是可选项，
而不是必须经过的阶段。

本评测入口使用官方的当前任务指令。每次调用 `vla_execute` 时，都必须将
`robots.behavior_r1pro.effective_prompt` 原样复制为指令；当前局部阶段应写在
`PLAN.md` 和动作推理说明中，而不是改写策略提示词。`step` 是正整数的策略动作
执行预算，不得超过 `robots.behavior_r1pro.max_action_steps`。应分成有界的短段
执行，并在每段之间检查进展。

### `navigate_vln`

通过内置 `lightnav` 技能执行自然语言底盘导航：

```json
{"instruction": "Approach the requested object", "max_steps": 60}
```

驱动使用新的头部相机画面，并将其它关节保持在最近测得的位置。
本次预算用尽、模型建议停止或发生错误时，控制权返回 Agent。
同一轮任务中连接正常的多次调用会保留 LightNav 历史。
Agent 自主选择导航指令、预算和恢复动作。
`max_steps` 是本次调用预算，不能超过 `max_action_steps`；整轮步数上限仍由
官方评测器掌管。LightNav 需要独立的外部服务，不提供自动避障，也不能仅凭
`visible=true` 或模型停止信号证明已经到位。

### `adjust_posture`

可选地通过相对关节运动调整身体姿态或相机视角：

```json
{"joint_deltas_rad": {"torso_joint4": 0.1}, "max_steps": 40}
```

使用 `ROBOT_STATE.md` 中实测的 `body_posture`。有效名称为 `torso_joint1`
至 `torso_joint4`、`left_arm_joint1` 至 `left_arm_joint7`，以及
`right_arm_joint1` 至 `right_arm_joint7`。每个增量限制为 ±0.25 弧度，
单步最多变化 0.01 弧度，之后保持 10 步，并遵守 URDF 限位。
底盘速度设为零；其它关节与夹爪保持当前位置。头部相机固定在 `torso_link4`，
腕部相机固定在各自的夹爪上。连杆原点不是碰撞体积；此动作不检查环境碰撞或
自碰撞，也不会自动调整姿态。执行后应检查同步的实测姿态和画面；
目标关节跟踪误差超过 0.05 弧度时会报告失败。

### `move_to_pose`

将一个末端执行器移动到可到达的实测位置附近：

```json
{"side": "right", "position_m": [0.55, -0.18, 0.92], "coarse": true, "steps": 40}
```

`side` 为 `left` 或 `right`。`position_m` 必须来自 `object_location`
在 `robot_base` 坐标系下成功返回的结果，或者是根据该结果推导出的避障位置。
如果结果提供了目标物体或控件的边界框，应优先使用确定性的接触前目标形式：

```json
{
  "side": "auto",
  "bbox_world_min_m": [0.48, -0.12, 0.82],
  "bbox_world_max_m": [0.62, 0.02, 0.96],
  "standoff_m": 0.12,
  "coarse": true,
  "steps": 40
}
```

使用边界框时，驱动找到朝向所选手臂的表面，请求距表面 8–15 厘米的目标点，
而不是物体占据的中心点。包围盒目标可用 `auto` 选择更近的手臂，不设手别偏好。
显式提供 `position_m` 时，`side` 必须为 `left` 或
`right`。`orientation_quat` 使用 XYZW 顺序。省略该字段时，两种运动原语
的精确运动均保持当前手腕姿态。

`coarse` 是仅用于 `move_to_pose` 的可选布尔参数（默认 false），不是全局
控制模式。为 true 时，一次有界求解寻找朝向请求点的可达位置，不会仅因厘米级
位置或朝向误差拒绝粗接近。显式提供的朝向，或省略时的当前朝向，均作为软偏好；
不保证求得全局最近点。结果中的 `Coarse approach plan` 包含 `robot_base` 下的
`requested_position_m`、`planned_reachable_position_m` 和 `remaining_distance_m`。
该终点来自 URDF 正向运动学，不代表实测到位、目标身份正确或抓姿可用。
运动后重新读取实际状态和画面，不要仅为消除剩余距离重试。求解失败、没有有效
接近进展、坐标无效或规划终点落入所提供的物体边界框时，仍会阻止下发；
不保证整条路径无碰撞。为 false 或省略时，保持原来的精确位姿 IK 检查。

`move_to_pose` 的两种目标形式以及 `move_linear` 均接受可选的 `steps` 和
`settle_steps`，包括通用 attach 示例中的用法。`steps` 是正整数，指定运动
至少持续的步数，而不是到数就提前停止的预算；省略时按关节和路径限制自动规划
时长。如果请求步数短于安全轨迹，驱动会延长，绝不加速或截断尚未到达目标的
运动。`settle_steps` 是非负整数（默认 0），在运动完成后追加实际的末端保持
指令。运动与保持的总步数必须满足驱动的 `primitive_max_steps` 上限（默认
240）；否则在下发前拒绝执行。这些时长参数不会选择粗接近 IK，也不会放宽坐标检查或
关节限位，也不能证明路径无碰撞。

### `move_linear`

沿笛卡尔直线，将一个末端执行器移动到可到达的实测位置，或移动指定的相对位移：

```json
{"side": "right", "delta_m": [0.0, 0.0, 0.08], "steps": 30, "settle_steps": 20}
```

仅在短距离的最后接近、抬起或沿可见空旷路径撤离时使用。`position_m` 绝对位置
与 `delta_m` 相对位移必须且只能提供其中一个；`orientation_quat` 可选。
时长遵循上述 `steps` 和 `settle_steps` 约定；保持阶段重复最终指令，
不会追加笛卡尔位移。

### `set_gripper`

```json
{"side": "left", "command": "open", "steps": 15}
```

`command`（`open` 或 `close`）与 `opening_m`（0.0–0.1 米）必须且只能提供
其中一个。`steps` 可选。只有当前计划和可见几何信息给出了具体理由时，才应
闭合夹爪。

### `hold_position`

```json
{"step": 1}
```

保持当前关节与夹爪位置，并将底盘速度设为零。仅用于同步或诊断。
Agent 推理本身不需要这个动作，因为动作之间仿真器已暂停。

`gateway_status` 仅供读取。`attach` 是组合受支持的 `move_to_pose`、
`move_linear` 和 `set_gripper` 动作的通用 EMERGE 技能，不是独立的驱动动作。
该驱动尚未实现 `follow_arc`。

每个本地运动原语都受到官方关节限位和单步关节变化上限约束。下发动作前，驱动会
将 URDF 正向运动学计算结果与观测到的末端执行器位置进行比较；若坐标约定不一致，
则拒绝执行。切回 OpenPI 策略时，仅使缓存动作与 rolling-inpainting 的衔接
初值失效，以便根据运动后的新观测重新规划。LightNav 运动后也采用这一做法。
任务 ID、当前子任务阶段、阶段投票历史、底层策略状态与计数器都会保留；
交接不会让任务从阶段 0 重新开始。未插入本地运动的连续 VLA 调用保留正常的
动作缓存。只有官方新 episode 重置或切换任务时，才执行原有的完整阶段重置。
冠军服务必须声明支持 `invalidate_action_cache`；交接时遇到旧服务会拒绝执行，
不会回退为完整重置。运行本集成前需要重启更新后的冠军服务。
外部运动和重新生成动作仍与不间断的冠军 baseline 执行不同。

## 结果与成功判定

动作结果中的 `step_completed` 只表示指定的动作步数已经执行完毕，并与仿真器
状态完成同步；它不表示任务成功。唯一权威的成功信号是
`evaluation.success == true` 且 `evaluation.phase == "completed"`。
当 `evaluation.done` 为 true 时，应立即停止下发动作。
`evaluation.phase == "error"` 表示评测器故障，而非任务失败。任务运行期间，
`evaluation.steps` 尚不可用；`runtime_progress.gateway_action_steps` 仅是实时诊断
计数，不是官方评分。判断最近一次动作的结果前，应检查 `state_synced`。
